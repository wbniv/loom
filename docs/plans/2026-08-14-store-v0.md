# Plan — Store v0: the persistent content-addressed object store, in Rust

**Date:** 2026-08-14
**Status:** Built and verified — see [Run log](#run-log) and
[Recorded verification](#recorded-verification)
**Parent:** [SPEC §5](../../SPEC.md) (the store), sequenced by the
[masked-generation experiment](2026-08-13-masked-generation-experiment.md)
("experiment next; full store afterward") — the experiment is complete and its
store-shaping conclusions are recorded there.
**Language:** Rust, per
[the production-language decision](2026-08-14-production-language-decision.md)
Track G — greenfield, no contract, no oracle, no port. Building this **is**
trigger M2 firing ("the §5 store leaves memory"), and the decision's answer is
recorded there: Track G starts in Rust from the first line. Python remains the
validation oracle throughout.

## Objective

Replace the experiment's disposable in-memory resolver with the first durable
Loom store: content-addressed objects on disk, admission through the Python
validator chain, and a read API shaped like the one the experiment measured —
whole-definition retrieval for prompting, decode-time-cheap type lookup, and
hash-prefix queries for the masker. Small enough to land in one increment;
real enough that every later store feature (namespaces, leases, policy
admission, GC) extends it rather than replacing it.

## What the experiment settled, and this plan obeys

The six store-shaping conclusions (recorded in the parent plan), restated as
requirements:

1. **Whole-definition retrieval is the primary read path** — the corpus in
   context was the largest lever measured (95.8 % → 71.5 % rejection). The
   store serves full canonical surfaces cheaply, not just hash→type rows.
2. **Lookup misses are data.** A miss is a first-class, typed refusal the
   consulting layer reports as its own rejection — never a crash, never a
   silent default. Exit codes and output shape encode it.
3. **`reference_type` sits on the decode hot path** (3.15 ms/token total mask
   budget, measured). The type lookup must be O(1) against an index, no
   object parse on the read.
4. **Content-addressed identity is generation equality.** Byte-identical
   canonical objects deduplicate by construction; `put` of an existing hash
   is a no-op that reports `exists`.
5. **The store will not buy composition** — so nothing in v0 pretends to;
   provenance (which objects came from generation vs transpilation) rides in
   the meta-object, honestly.
6. **Decode-time store lookups are affordable in Python today** — so the
   masker keeps its in-process caches and consults the store only at
   resolver-construction time in v0. No RPC on the token path.

## Rules

### R1 — v0 scope: hash-addressed persistence, nothing that needs a lease

**In:** immutable content-addressed objects (definitions, ability/data
declarations, externs, meta-objects) as canonical CBOR bytes; SHA-256
identity verified on every write *and* every read; admission gated by the
Python oracle; the read API below; `fsck`; crash-safe writes.

**Out, explicitly, with the reason:**
- **Namespaces and leases** — SPEC §5.3 requires a store without leases to
  *refuse* namespace writes; v0 refuses by not having namespace writes at
  all. The lease protocol is open problem 4; building around it would decide
  it by accident.
- **Policy admission and evidence enforcement (§6.3)** — monotone assurance
  binds *bindings*, and v0 has no bindings. Evidence objects may be stored
  as opaque objects; nothing enforces their lattice yet.
- **GC** — nothing can be unreachable until bindings exist.
- **Network service** — v0 is a local, single-writer store behind a CLI.
  M2's "persistence or network" fires on persistence; the network half is a
  later increment on the same object layout.
- **Rust-side validation** — admission trusts the Python oracle (Track P
  owns re-validation in Rust, gated by the differential harness; see the
  language decision). The store *does* verify identity (hash of bytes) in
  Rust, because that is its own invariant, not a ported one.

### R2 — The object layout is the contract, and it is boring on purpose

```
store/
  objects/<2-hex>/<62-hex>          # canonical CBOR bytes, named by SHA-256
  meta/<2-hex>/<62-hex>.json        # oracle-produced sidecar (R3)
  index/types.jsonl                 # hash → kind, type surface (rebuildable)
  store.json                        # layout version, contract versions
```

Git-style fan-out over the hash; the object file's content hashes to its
name, and `fsck` re-verifies exactly that. Every file is written
tmp-then-rename (atomic on one filesystem), so a crash leaves either the old
state or the new one, never a torn object. The index is derived data —
deleting it and rebuilding from sidecars must be lossless (`fsck` checks
this too). No embedded database in v0: the KV problem here is "content-
addressed immutable blobs", which a filesystem already solves debuggably;
an index that outgrows a JSONL scan is the trigger to revisit, recorded
as a completion-criteria watch, not built now.

### R3 — Admission: the oracle validates, the store stores, and both say so

`put` runs the object through the Python chain (transcode → scope →
references → typecheck, via a thin `prototype/` entry point) and refuses on
any rejection, echoing the layer's own error class — conclusion 2's shape at
admission time. On acceptance the oracle emits the sidecar the store cannot
produce itself in v0 (kind, type surface, declared dependencies, provenance,
contract versions at admission); the Rust store verifies the bytes hash to
the claimed identity and lands object + sidecar + index row atomically.
Objects admitted under different contract versions are distinguishable by
their sidecars — the store records the versions, and a future MAJOR bump can
find every object that predates it.

### R4 — The read API is the experiment's resolver, persistent

CLI subcommands (machine-readable one-line JSON on stdout, human-oriented
only in `--verbose`):

- `get <hash>` — canonical bytes (conclusion 1); miss → exit 3, typed error.
- `type <hash>` — type surface from the index, no object parse (conclusion 3).
- `deps <hash>` / `rdeps <hash>` — declared dependency edges from sidecars.
- `list [--kind K]` — enumerate hashes+kinds (prompt-corpus assembly).
- `prefix <hex>` — all hashes extending a prefix (the masker's ref-hash trie
  is seeded from exactly this).
- `put --sidecar <json> <file>` / `admit <file>` (admit = oracle + put).
- `fsck` — every object re-hashed, every index row re-derivable, every
  sidecar hash-matched; exit 0 only if all three hold.
- `export-resolver` — one JSON document with everything
  `experiment.resolver.ExperimentResolver` needs, so the harness constructs
  its resolver from the store in one read (conclusion 6: no per-token IPC).

The Python harness gains a `StoreResolver` that consumes `export-resolver`
and is behaviorally identical to the corpus-built resolver — proven by
running the existing resolver-dependent test modules against both.

### R5 — Seeding: the corpus is the first tenant

`task store:seed` admits the full pinned corpus — 26 definitions, 8
abilities, 4 data declarations, 9 externs — through `admit`, then `fsck`s.
The seeded store becomes the fixture for every Rust-side test that needs
real objects, and `StoreResolver`-vs-corpus-resolver equivalence over it is
the v0 acceptance gate.

### R6 — Toolchain via task, pinned

`task setup` grows a Rust section: rustup installed under `~/.rustup` with a
**pinned stable toolchain** (1.89 series, verified current at implementation
time), `cargo --version` echoed, idempotent re-run. The crate lives at
`store/` (workspace-ready), `cargo build/test/clippy/fmt` wired as
`task store:build` / `store:test` / `store:lint`. Dependencies held to:
`sha2`, `serde`/`serde_json`, `clap`, `tempfile` (dev) — no CBOR crate
(bytes are opaque in v0, per R1), no async runtime, no embedded DB.

### Decisions taken inside the plan's shape

**The toolchain pin is 1.97.1, not the 1.89 series R6 guessed at.** R6 said
"verified current at implementation time"; `channel-rust-stable.toml` on
2026‑08‑14 reports 1.97.1 (release date 2026‑07‑16), so that is what
[`store/rust-toolchain.toml`](../../store/rust-toolchain.toml) pins.
`task setup` installs that exact toolchain and deliberately never touches
`rustup default`, which is a machine-wide setting other projects own.

**Definitions travel as their surface; declarations travel as a JSON mirror of
their IR.** §5.1 declarations have no surface syntax, so something had to carry
them. The alternative considered and rejected was writing a canonical-CBOR
*decoder* in Python: it is comparable work, it would sit inside the `parser`
contract's blast radius for no conformance gain, and it produces bytes nobody
can read in a debugger. The mirror is checked rather than trusted — admission
decodes it back and requires `declaration_hash` to survive the round trip, and
`StoreResolver` hands the reconstructed object to `DeclarationRegistry.add`
*with* its expected hash, so a mirror that disagreed with the CBOR encoder
fails loudly at both ends and can never be landed silently.

**The index carries `sidecar_sha256`, and that is what makes "fsck catches a
deliberately edited sidecar" true rather than nearly true.** Without it, `fsck`
would only catch edits to fields it happens to index — an integrity check whose
coverage nobody could remember. With it, any byte changed in any sidecar makes
the stored index differ from a rebuild, including `spec`, which no store query
ever reads. Demonstrated in step 8 below.

**Sidecars carry a `sequence` and no timestamp.** The completion criterion is
that a re-seeded store is byte-identical, so nothing in the store may be a wall
clock. `sequence` is the admitter's presentation order, which for the pinned
corpus is the manifest's dependency order — the thing
`ExperimentResolver.definitions()` promises and that a content-addressed store
otherwise has no way to reproduce, since it never invented the order in the
first place.

**Admission threads the §3.3 subsumption collector; `evaluate.run_funnel` does
not.** A `refine`-carrying corpus entry cannot reach the `checked` tier without
it (`test_corpus` threads the same collector for the same reason). The two have
different jobs — the funnel scores what a model produced under default rules,
admission decides what may enter the store — so admission runs the deepest
validation available and records the obligation count in the sidecar.

**`export-resolver` re-emits whole sidecars rather than a narrower projection.**
A projection would be a second schema to keep in step with the first, and the
first is already the oracle's statement of record.

**Rejected:** a `--store` daemon or any RPC (conclusion 6 says the harness reads
once at resolver-construction time, so a process boundary per token buys
nothing); storing the resolver export inside the store as a maintained artifact
(it is derived, and a derived file that is not `fsck`ed is a second index
nobody checks); and making the Rust tests depend on a pre-seeded store — they
build their own in tempdirs, and the corpus-seeding tests shell out to the
oracle at `../prototype`, which is the only dependency worth having.

### The sidecar schema

Version 1, documented in full in
[`prototype/store_admit.py`](../../prototype/store_admit.py)'s module docstring:
`schema`, `hash`, `kind`, `name`, `type_surface`, `deps`, `surface`
(definitions), `object` (declarations, as the JSON mirror), `spec`, `sequence`,
`provenance` (`origin`/`source`/`admitter`, plus `artifact` + `abi` for externs
and `nominal_key` for data and ability declarations), and `validation`
(`layers`, `contracts`, `obligations`).

`deps` excludes identity slots — a declaration's nominal key and an extern's
pinned artifact are 32-byte values naming something that is *not* a store
object, and reporting them as dependencies would invent edges to hashes the
store can never hold. The corpus's nominal keys really are disjoint from its
store hashes, so the exclusion is load-bearing rather than vacuous
(`test_store.py::test_dependency_edges_exclude_identity_slots`).

  `StoreResolver(export-resolver)` with byte-identical prompts to the
  corpus-built path.

  sidecar.

  ever profiles above milliseconds, that is the trigger to revisit R2's
  no-database stance.
